# Finish GPU inventory before fairshare

**Follow-up (2026-11-12):** User requested research + **add them all**. Approved implement scope = Immediate + P0 + P1 in the tiered backlog below (not Run:ai/MLOps). Plan updated; coding blocked until Agent mode is accepted.

Axiom’s highest-value next GPU work is not a new accelerator platform—it is **closing the vertical slice on inventory already modeled in-repo**. Untracked platform code already builds an `AcceleratorsReport` (nodes, pods, MIG maps, GPU Operator / device-plugin / DCGM presence, ClusterPolicy GVR) and populates Node/Pod GPU fields on list paths, yet **`GET /api/v1/accelerators` is unregistered**, the frontend has **no Accelerators page or GPU columns**, and ROADMAP/GAPS are silent on NVIDIA. Against Portainer’s dedicated GPU tables, OpenShift’s overview DCGM tiles, and Lens/Headlamp DRA browsers, that gap is the competitive miss. Immediate priority is the thin API + Ops/Accelerators UI + docs pack; P0 then adds GFD sharing/MIG state clarity, ResourceQuota pressure, and dual-family DCGM PromQL. Fairshare, fractional GPU admission, model catalogs, and Run:ai-class scheduling stay out of scope for zyvor-axiom as a k8s-native private-cloud console.

## Partial NVIDIA stack already waits on HTTP and UI

Platform types already carry the inventory contract competitors treat as table-stakes. `Node` exposes GPU capacity/allocatable, product, driver, and a MIG quantity map; `Pod` carries a GPU request string; dedicated types (`AcceleratorsReport`, `AcceleratorsOperator`, `AcceleratorNode`, `AcceleratorPod`) document the intended **`GET /api/v1/accelerators`** route, and both Demo and Kubernetes providers implement `ListAccelerators` via helpers that apply GFD-style labels and DaemonSet heuristics for device-plugin, DCGM exporter, and gpu-operator ([types.go](file:///Volumes/Storage/tt/axiom/internal/platform/types.go); [nvidia_gpu.go](file:///Volumes/Storage/tt/axiom/internal/platform/nvidia_gpu.go); [nvidia_gpu_kubernetes.go](file:///Volumes/Storage/tt/axiom/internal/platform/nvidia_gpu_kubernetes.go); [kubernetes.go](file:///Volumes/Storage/tt/axiom/internal/platform/kubernetes.go)). Live list paths already call `applyNodeGPUFields` and `podGPURequest`, so JSON consumers can see GPU data even without a dedicated page ([kubernetes.go](file:///Volumes/Storage/tt/axiom/internal/platform/kubernetes.go)).

The break is above the provider. Ripgrep finds **zero** accelerators handlers under `internal/api`; `server.go` registers nodes, pods, cost, gateways, metrics history, and agent-runs but not accelerators; `docs/API.md` has no accelerators section despite the type comment promising the route ([server.go](file:///Volumes/Storage/tt/axiom/internal/api/server.go); [API.md](file:///Volumes/Storage/tt/axiom/docs/API.md)). Frontend search likewise finds no Accelerators route or GPU columns: `Nodes.jsx` shows CPU/memory/pods allocatable only, `PodDetail.jsx` ignores GPU, `App.js` has no `/accelerators`, and Ops Cost breakdown renders `cpu · mem · storage · net` while omitting `otherUsd`—even though OpenCost’s `gpuCost` is already ingested and folded into `OtherUSD` on the server ([Nodes.jsx](file:///Volumes/Storage/tt/axiom/frontend/src/pages/Nodes.jsx); [Ops.jsx](file:///Volumes/Storage/tt/axiom/frontend/src/pages/Ops.jsx); [cost_opencost.go](file:///Volumes/Storage/tt/axiom/internal/platform/cost_opencost.go)). Prometheus builders remain cAdvisor CPU/memory only; rightsizing apply explicitly rejects `"gpu"`; DCGM is detected as an inventory badge and never queried ([prometheus.go](file:///Volumes/Storage/tt/axiom/internal/platform/prometheus.go); [cost_rightsizing_apply.go](file:///Volumes/Storage/tt/axiom/internal/platform/cost_rightsizing_apply.go)).

**Immediate finish-the-pack** is therefore a small vertical slice, not greenfield modeling: register `GET /api/v1/accelerators` calling `provider.ListAccelerators`; add Ops → Accelerators (or `/accelerators`) with Portainer-like node/workload tables; surface existing `GPU` / `AllocatableGPU` / `GPUProduct` / MIG fields on Nodes and PodDetail; split or surface GPU spend (`gpuUsd` from already-parsed `gpuCost`, or at least show `otherUsd`); and acknowledge the pack in ROADMAP/GAPS/API.md. Prefer GFD inventory labels (`nvidia.com/gpu.product`, `.count`, `.memory`, `.replicas`, `.sharing-strategy`, MIG labels, `cuda.driver-version.full`) and Operator `nvidia.com/gpu.deploy.*` / ClusterPolicy `status.state` for readiness—treat NFD PCI / `gpu.present` as hints only, requiring allocatable extended resources or healthy device-plugin pods before calling a node schedulable ([GFD README](https://github.com/NVIDIA/k8s-device-plugin/blob/main/docs/gpu-feature-discovery/README.md); [kubectl-nv labels](https://github.com/NVIDIA/kubectl-nv/blob/main/docs/labels.md); [aicr health-check](https://github.com/NVIDIA/aicr/blob/main/recipes/checks/gpu-operator/health-check.yaml)).

## Portainer-class inventory beats Run:ai for Axiom’s lane

General consoles win on inventory and observability, not on hierarchical fairshare. Portainer Business Edition ships a dedicated GPU view: per-node Ready/Degraded badges, capacity/allocatable/allocated for `nvidia.com/*`, GPU Operator and device-plugin detection, GPU Nodes and GPU Workloads tables with scheduling issues, plus cluster summary tiles ([Portainer GPU docs](https://docs.portainer.io/user/kubernetes/gpu)). OpenShift’s NVIDIA console plugin adds Home Overview tiles (available GPU count, power W, encoder/decoder %) and Observe-hosted DCGM Grafana graphs (temperature, power, SM clocks, utilization, framebuffer) without leaving the admin console ([OpenShift GPU dashboard](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/openshift/enable-gpu-op-dashboard.html); [OpenShift DCGM dashboard](https://docs.nvidia.com/datacenter/cloud-native/openshift/latest/enable-gpu-monitoring-dashboard.html)). Lens and Headlamp 0.46 differentiate on **DRA** (`resource.k8s.io/v1` GA in Kubernetes 1.34): DeviceClasses, ResourceSlices, ResourceClaims, and claim state on pods/nodes ([Lens Device Resources](https://docs.lenshq.io/k8slens/using-lens/device-resources/); [Headlamp 0.46](https://github.com/kubernetes-sigs/headlamp/releases); [K8s 1.34 DRA blog](https://kubernetes.io/blog/2025/09/01/kubernetes-v1-34-dra-updates/)).

MIG and time-slicing **configuration** remain YAML/ClusterPolicy even on OpenShift; consoles that matter surface **state**—`mig.config` / `mig.config.state`, `sharing-strategy`, `replicas`, `-SHARED` product suffix, mixed-strategy `nvidia.com/mig-*` capacity keys—rather than rebuilding NVIDIA’s partition editor ([GPU Operator MIG](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/gpu-operator-mig.html); [GPU sharing](https://docs.nvidia.com/datacenter/cloud-native/gpu-operator/latest/gpu-sharing.html)). Scheduling UX that belongs in Axiom stops at ResourceQuota used/hard for `requests.nvidia.com/gpu` (and discovered MIG names) plus pending GPU pods with FailedScheduling reasons ([OCP quotas](https://docs.redhat.com/en/documentation/openshift_container_platform/4.21/html/scalability_and_performance/compute-resource-quotas)). Run:ai / KAI deserved-vs-over-quota, time-based fairshare, preemption, and fractional GPU annotations, Volcano fairshare plugins, and Domino Hardware Tiers are scheduler/ML-platform products—not private-cloud console MVPs ([Run:ai concepts](https://run-ai-docs.nvidia.com/self-hosted/platform-management/runai-scheduler/scheduling/concepts-and-principles); [KAI queues](https://github.com/NVIDIA/KAI-Scheduler/blob/main/docs/queues/README.md); [Domino hardware tiers](https://docs.dominodatalab.com/en/6.2/admin_guide/c3aaf3/create-a-hardware-tier/)).

Metrics differentiation without MLOps is DCGM→Prometheus with honest empty states, plus usage-based idle/efficiency. NVIDIA’s path is GPU Operator → DCGM Exporter (commonly `:9400/metrics`) → Prometheus → Grafana 12239 ([GPU Telemetry](https://docs.nvidia.com/datacenter/cloud-native/gpu-telemetry/latest/); [DCGM Exporter](https://docs.nvidia.com/datacenter/cloud-native/gpu-telemetry/latest/dcgm-exporter.html)). Kubecost/OpenCost build GPU efficiency and idle cost on `DCGM_FI_PROF_GR_ENGINE_ACTIVE`, with documented holes for time-sliced shared containers and product-vs-OSS disagreement on MIG ([Kubecost NVIDIA config](https://www.ibm.com/docs/en/kubecost/self-hosted/2.x?topic=configuration-nvidia-gpu-monitoring-configurations); [Apptio GPU monitoring](https://www.apptio.com/blog/gpu-monitoring/); [opencost#2853](https://github.com/opencost/opencost/pull/2853)). Axiom already folds OpenCost `gpuCost` into `otherUsd` invisibly; surfacing that dollar signal is a console win below Run:ai and above “link to Grafana.”

## Out of scope keeps Axiom a private-cloud console

Axiom owns cluster/node/pod/operator/metrics layers: inventory from capacity + GFD + ResourceSlices; Operator/device-plugin/DCGM health; MIG/time-slice **status**; namespace GPU quotas; unschedulable GPU workloads; DCGM util/power/memory/temp and idle-vs-requested; OpenCost-compatible cost attribution; optional read-only CRD browsers. That matches Portainer/Lens/OpenShift overview patterns and Axiom’s k3s-to-production console positioning—not Metal3-first or multi-runtime portability stories.

**Explicitly out of scope (defer to ML platforms / specialized schedulers):** model registries, fine-tune/serve wizards, playgrounds, and Inference Hub / KAITO-style model deploy ([Inference Hub](https://artifacthub.io/packages/headlamp/batuhancikrikci-headlamp-plugins/inference-hub); [KAITO](https://kaito-project.github.io/headlamp-kaito/)); project/department hierarchical fairshare with preemption editors; Hardware Tier catalogs and per-run cents billing products; experiment tracking, dataset lineage, notebook UX; automatic GPU node provisioning tied to model size; full BCM/Slurm-style HPC job accounting; training CUDA workload authoring; implementing KAI/Volcano/Run:ai scheduling itself. Boundary case that stays “integrate or deep-link”: show queue depth read-only if CRDs exist—never configure deserved GPU or fractional admission policy in Axiom.

Adjacent dirty-tree work **affects sequencing only lightly**. Agents, Alertmanager, MCP, metrics history, and Envoy Gateway already have mux registration and/or Ops UI hooks and ROADMAP 0.14 credit, while GPU inventory code sits untracked ahead of HTTP/UI and invisible in ROADMAP ([ROADMAP.md](file:///Volumes/Storage/tt/axiom/docs/ROADMAP.md)). That means the NVIDIA pack is the cheapest competitive close relative to effort already spent in `nvidia_gpu*.go`; it should not wait on agent/MCP write-tool polish. Conversely, after accelerators API+UI land, prefer polishing already-mux’d Alertmanager/agents over inventing GPU rightsizing—rightsizing apply remains CPU/memory-only by design ([cost_rightsizing_apply.go](file:///Volumes/Storage/tt/axiom/internal/platform/cost_rightsizing_apply.go)).

## Conclusion

The competitive bar for Axiom is Portainer’s GPU page plus OpenShift-grade DCGM overview and Lens-grade DRA detection—not Run:ai. Because inventory types and `ListAccelerators` already exist in the dirty tree, the decisive move is exposing them through API, Ops UI, cost columns, and docs before building new telemetry models. Once that slice ships, P0 sharing/MIG/operator-health clarity and dual-family DCGM queries convert “we detect DCGM” into “operators see waste and pressure,” while staying firmly on the private-cloud side of the MLOps line.
