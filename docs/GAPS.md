# Feature gaps (living)

Closed or substantially narrowed in the current tree (see CHANGELOG):

- SAML ACS sessions (`POST /api/v1/auth/saml/acs`) — the response's enveloped XML-DSig signature is verified against the pinned `AXIOM_SAML_IDP_CERT` (only the signed content is trusted, which defeats signature wrapping), and the audience (`AXIOM_SAML_ENTITY_ID`) and `NotBefore`/`NotOnOrAfter` window are enforced
- SAML `InResponseTo` and `SubjectConfirmationData` — `GET /api/v1/auth/saml/login` sends a real AuthnRequest with a random ID, recorded in a signed 5-minute `axiom_saml_req` cookie and in a single-use in-memory set; the ACS requires the signed `InResponseTo` to match both and consumes it, so a captured response cannot be replayed (not even in the same browser). Unsolicited (IdP-initiated) responses are rejected unless `AXIOM_SAML_ALLOW_IDP_INITIATED=true`. A `SubjectConfirmation` must use the bearer method, and its `SubjectConfirmationData` `Recipient` must equal this ACS URL and `NotOnOrAfter` must not have passed
- LDAP simple-bind via the local username/password form (`AXIOM_LDAP_*`)
- Operator role + safer OIDC default role env (`AXIOM_OIDC_DEFAULT_ROLE`)
- Fleet cluster register/unregister from kubeconfig (Settings → Clusters)
- HA: Helm fails when `replicaCount > 1` without `auth.sessionSecret`
- Audit ring default raised to 5000 (`AXIOM_AUDIT_RING_SIZE`)
- ConfigMap/Secret update; Velero on-demand backup; VM create/delete; PVC/Service/Ingress/Quota writes; Helm upgrade
- VM console returns proxied `wsPath` for browser VNC clients
- OIDC login validated end-to-end against a real Keycloak IdP (public client + PKCE, no client secret needed) — see `e2e/scripts/verify-sso.js`
- Enterprise write endpoints validated against a real cluster, not just the demo provider/fake clientsets — see `e2e/scripts/validate-enterprise-writes.sh`. Found and fixed one real RBAC gap: `DELETE /api/v1/vms/{ns}/{name}` was 403ing because the `zyvor-axiom` ClusterRole never granted `delete` on `kubevirt.io` VMs
- Login throttling is per client IP **and** per attempted account name (`internal/auth/ratelimit.go`); a valid login from another account can no longer reset the counter of an account being guessed. Trade-off: anyone who knows a username can lock that account for up to 5 minutes by failing logins
- OIDC ID tokens are verified against the provider's JWKS (algorithm allow-list, `kid`, signature, `iss`/`aud`/`azp`/`exp`/`sub`) and bound to the sign-in by a `nonce` cookie (`internal/api/oidc_jwks.go`)
- Browser WebSocket/EventSource auth uses single-use, 30-second tickets (`POST /api/v1/ws-ticket`) instead of credentials in the URL; the legacy `?access_token=`/`?axiom_session=`/`?api_key=` forms still work but are deprecated

- Plain-http OCI registries can be installed from: a repository added over plain http (with `AXIOM_HELM_ALLOW_INSECURE_REPOS`) is recorded as `plainHttp` and its charts are installed and upgraded with `helm … --plain-http`
- Fleet health: registered clusters are probed in the background and reported healthy / degraded / unreachable with latency and the last error (`GET /api/v1/fleet`, the Fleet page, the switcher dot); state changes are audited

Known UI limitations (reviewed, not yet fixed):

- **Not translated, by design:** Kubernetes kinds and API terms (Pod, Namespace, Deployment, StorageClasses, NetworkPolicies, …), YAML/JSON, field paths, metric names, units (`MiB`, `GiB`, `m`, `vCPU`), `kubectl`/`virtctl` commands, example placeholders (`tenant-b`, URLs, cron expressions, and the Workloads intent example, because the intent parser only understands English keywords), product names (Anthropic, Ollama, Argo CD, Flux), Kubernetes enum values (`NoSchedule`, `ReadWriteOnce`, KEDA `Auto`), and everything the API returns (error messages, event messages, health and security findings, rightsizing notes, AI answers)
- **Not translated yet:** nothing known; `lint:i18n --verbose` lists no unconverted literals (its allow-list holds the by-design terms above). Usernames and role *values* stay as stored and sent (`admin`/`operator`/`viewer` from `/users`, `Viewer`/`Platform Admin` from `/session`); only the role label shown is translated, and an unknown value is shown as sent. In English the Users table keeps the lower-case role names it always showed
- **English wording quirks are kept on purpose:** where the English UI always printed a plural ("1 nodes total", "1 keys", "1 charts") the English string is unchanged so existing tests stay valid; German, Spanish and French use the correct singular
- **No right-to-left support.** Dates and numbers follow the UI language, not a separate regional setting, and money is always USD (the cost model's currency)

Known security limitations (reviewed, not yet fixed):

- **Two-factor sign-in does not cover SSO accounts** (they rely on the IdP's MFA), and a person who loses both their device and their recovery codes needs an administrator to reset it. A directory account's enrolment status may take up to 5 s to reach other replicas (codes themselves are always checked against the shared Secret)
- **Outstanding SAML AuthnRequests are in-memory per replica** (capped at 4096, oldest evicted first). With `replicaCount>1` the `/saml/login` redirect and the IdP's POST to `/saml/acs` must reach the same replica (session affinity), otherwise the sign-in fails with "unknown, expired or already used". The ACS URL is derived from the request (`X-Forwarded-Proto`/`X-Forwarded-Host`), so the proxy must pass the public scheme and host for the `Recipient` check to match. With `AXIOM_SAML_ALLOW_IDP_INITIATED=true`, unsolicited responses are bound only by their validity window and Recipient, not to a browser, and can be replayed within that window
- **Stream tickets are in-memory per replica.** With `replicaCount>1` a ticket is only redeemable on the replica that issued it, so WebSocket/SSE connections need session affinity (or a single replica); the login throttle counters are likewise per replica
- **The in-origin pod HTTP proxy (`/pods/{ns}/{name}/window/{port}/`) still accepts `?access_token=` for plain browser navigations** when the separate pod proxy origin is off (the default): it loads many sub-resources, so a single-use stream ticket cannot cover it. With `AXIOM_POD_PROXY_ADDR`/`AXIOM_POD_PROXY_ORIGIN` set, that route answers `410` and the UI uses single-use `window-link` tickets and a proxy-origin session cookie instead, so no console credential is put in a URL
- **Session revocation is eventually consistent across replicas.** Logout, sign-out-everywhere and account changes apply at once on the replica that handled them and on the others within `AXIOM_REVOCATION_REFRESH` (default 15 s) through the shared ConfigMap. A role change at an SSO identity provider is still only picked up at the next sign-in (an administrator can force that with "Sign out everywhere")
- **The separate pod proxy origin is opt-in and off by default.** Without `AXIOM_POD_PROXY_ADDR`/`AXIOM_POD_PROXY_ORIGIN` the pod "window" proxy still serves pod content from Axiom's own origin (CSP sandboxed into an opaque origin, cookies stripped, operator-only). With it on, pod content is isolated from the console on its own origin. With the `{id}` host form (`AXIOM_POD_PROXY_ORIGIN=https://{id}.pods.example.com`, host mode) every pod session also gets an origin of its own, served at the root, so pod pages cannot see each other's storage or cookies and absolute paths work; it needs wildcard DNS and a wildcard certificate (or `*.localhost` in a lab; Safari may not resolve that). With the fixed-origin form every pod opened through the proxy shares that one origin (pod pages can see each other's `localStorage`, though not the HttpOnly, path-scoped session cookies), and a pod's redirects or absolute links to `/…` leave its `/s/<sid>/` prefix and 404. Remaining in both modes: signing out of the console session that created a pod session does not end it (only a per-user revocation — sign out everywhere, password/role/namespace change, deletion — or its own 10-minute idle / 1-hour limit does); and a same-host, different-port setup still shares the browser's cookie jar with the console (the listener ignores console cookies, but use a separate hostname)
- **Pod proxy across replicas is best effort in three places.** With `AXIOM_SESSION_SECRET` set, pod proxy tickets and session cookies are signed tokens any replica accepts (no session affinity needed). (1) *Single use of a ticket across replicas* rests on the `zyvor-axiom-pod-proxy-redeemed` ConfigMap: a redeem reads and conditionally updates it (resourceVersion-guarded, retried on conflict), so two replicas racing on one ticket cannot both win while the API server answers. If that read or write fails (API server unreachable, RBAC removed, retries exhausted under heavy contention) the failure is logged and the ticket is checked against the redeeming replica's memory only, so for the rest of its 60-second life it could be redeemed once more on each other replica; the replay still needs the ticket itself (a single-use URL handed to the operator's browser) and yields a session for the same user, pod and port, subject to the same revocation checks. Each redemption costs one ConfigMap read and write. (2) *Per-user caps* (16 outstanding links, 32 live sessions) are counted per replica, so with N replicas a user can hold up to N times as many. (3) *Ending a session early* is still only by per-user revocation (or the idle/maximum limits): a signed cookie cannot be withdrawn, and a revocation made on another replica applies within `AXIOM_REVOCATION_REFRESH` (default 15 s). In host mode a replica that did not create a session cannot tell an unknown session id from one whose request came without a valid cookie, and answers both with the empty `404` (the creating replica still answers `403` to a live session without its cookie). A browser that does not store the re-issued cookie (sent at most once a minute while the session is in use) keeps its session only on the replica that created it. Without a session secret everything stays in one process's memory and a multi-replica install needs affinity
- **LDAP over `ldap://` is plaintext** (no StartTLS); use `ldaps://`. `AXIOM_LDAP_BIND_DN`/`AXIOM_LDAP_BIND_PASSWORD` are read but unused.
- **Default credentials**: the Helm chart and manifest default to `demo`/`demo`. Axiom logs a warning outside demo mode, and no longer advertises them on the login page, but does not refuse to start.

Known platform limitations (reviewed, not yet fixed):

- **OCI registry credentials are one username/password (or access token) per credential, sent as HTTP Basic or exchanged for a bearer token.** Token-based registry auth flows that need a cloud identity — AWS ECR (`aws ecr get-login-password`), GCR/Artifact Registry service-account keys or workload identity, Azure AD tokens for ACR — are not supported beyond pasting a short-lived token as the password (which then has to be rotated by delete + recreate). The credential's password goes only to its registry host and to a token realm on the same registrable domain; a registry whose token realm is on an unrelated site cannot be used with credentials. A plain-http registry's credentials travel unencrypted (only possible with `AXIOM_HELM_ALLOW_INSECURE_REPOS`). Install Jobs pull with `--plain-http` only for a reference that matches a repository recorded as plain http; an `ociRef` that matches no stored repository is pulled anonymously over https. Most hosted registries (ghcr.io, Docker Hub) do not offer `/v2/_catalog`, so their charts must be listed explicitly (at most 50 per repository); at most 500 tags per chart are read (in the registry's order), only tags that parse as semver are versions, and only the newest release's Chart.yaml is fetched, so older versions show no app version

- **GitOps repository credentials are not managed here.** Argo CD repository credentials are configured in Argo CD, and a Flux `secretRef` must name a Secret that already exists. Only the typed fields are supported (no multi-source Applications, ApplicationSets, Helm `valuesFrom`, or Kustomize patches)
- **VPA and KEDA editing covers the typed fields only.** VPAs with container policy `mode`/`controlledValues`, non-cpu/memory bounds, per-container controlled resources, `recommenders`, `evictionRequirements` or a non-`apps/v1` target, and ScaledObjects with `advanced`, `fallback`, `envSourceContainerName`, a non-`apps/v1` target, non-allow-listed trigger types or settings, `useCachedMetrics`, `metricType` on event triggers, a ClusterTriggerAuthentication or a credential-looking setting are shown read-only (`editable:false` with reasons); namespace, name and target cannot be changed
- **VPAs and KEDA ScaledObjects are limited to the typed model.** ScaledObject triggers are limited to the allow-listed types (cpu, memory, cron, prometheus, kafka, redis lists, rabbitmq, aws-sqs-queue) and settings; anything else (other scalers, `advanced`, `fallback`, `idleReplicaCount`) must be applied as YAML. KEDA `ScaledJob`s are not shown, TriggerAuthentications are listed by name only and cannot be created (use `POST /api/v1/apply`), ClusterTriggerAuthentications are not offered, and HPA creation only offers CPU/memory Utilization targets (other metric types are displayed but must be applied as YAML)
- **GitOps editing and credentials cover the typed fields only.** Applications that use multiple Argo sources, ApplicationSets, Helm `valuesFrom`/`valuesObject`, Kustomize patches/postBuild or `chartRef` are shown read-only; a Flux source that Axiom did not create, or that other objects share, keeps its URL/revision/secretRef read-only. Repository credentials cannot be updated (rotate = delete + recreate) and cannot be read back; only Secrets with the Argo CD repository labels or Axiom's own credential labels are ever listed (arbitrary Secrets never are), and only Axiom-labelled ones can be deleted. Argo CD known hosts, GitHub App and cloud-provider credentials are not managed here
- **Without OpenCost, cost figures are estimates of requested resources at flat rates** (20 USD per core, 5 USD per GiB per month), not usage and not your cloud bill. OpenCost (`AXIOM_OPENCOST_URL`) is the only source of actual cost: the experimental invoice reconciliation (below) only compares monthly totals, OpenCost covers only the cluster Axiom starts on, and its numbers are its allocation model (on-demand list prices unless OpenCost is configured with your pricing), scaled from the window to 30 days. Rightsizing savings are always priced at the request rates
- **Cloud bill reconciliation is experimental and unverified against real accounts.** The AWS, Azure and GCP clients were written from the providers' documentation and tested only against httptest fixtures (plus AWS's published SigV4 example); real responses may differ (paging, amortised vs. unblended cost, credits, tax, marketplace charges, currency conversion) and nothing has been checked against an actual invoice. It compares monthly totals only, for one account / subscription / export table and an optional single tag filter: no per-namespace attribution, no AWS CUR, no Azure billing-account or EA scope, no AWS session tokens or IAM roles (static access keys only), no Azure managed identity or GCP workload identity, no outbound proxy. *Allocated* is today's run-rate prorated over the month, not historical allocation, and the difference is shown only when the invoice is in USD. Invoice figures can lag the provider by up to a day plus the one-hour cache
- **Rightsizing is a recommendation and is never applied automatically.** The metrics-snapshot source (no `AXIOM_PROMETHEUS_URL`) is one current sample, so its verdicts are low confidence; Prometheus covers only the cluster Axiom starts on (clusters registered later use the snapshot); requests are read from the newest running pod, so a workload scaled to zero or mid-rollout may be misjudged; Jobs, CronJobs and bare pods are not assessed, and VPA targets are not used yet

Demo mode keeps it in memory only. Probes use the same credentials the console uses for that cluster. Each replica probes on its own. - **Audit persistence with several replicas**: each replica keeps its own ring and `Save` is an unconditional update, so the last writer wins. (A single replica is fine; the persisted ring is now trimmed to stay under the ConfigMap size limit.)
- **Generic manifest apply uses forced server-side apply**, which still takes field ownership from Argo CD/Flux/Helm — but the apply dialog now shows a diff first and warns when another manager owns the fields. - **Alert dispatch has no leader election**: with `replicaCount>1` every replica posts the same Slack alert, and a flapping pod re-fires every minute.

- **Interactive terminals have no idle timeout or ping/pong**; a client that vanishes without closing leaves its PTY until the pod exits. (Concurrent sessions are now capped at 64 and frames at 1 MiB.)
- **Seal NetworkPolicy names omit the workload kind**, so a Deployment and StatefulSet with the same name collide; `Approve/DenyAgentRun` do not check the current state; `GetCRDInstance`/`DeleteCRDInstance` accept built-in groups (apps, batch, rbac).

Other known gaps found by the functional test pass (see `e2e/README.md`):

- `POST /api/v1/users` maps an unknown role to `admin` (`NormalizeRole`, documented as intentional; consider fail-closed)
- A saved Slack / webhook URL cannot be cleared from the UI (the API's `*Clear` flags have no control), and the Atlas token has no UI field
- `/api/v1/session` reports `role: "Platform Admin"` for operators and `auth: "oidc"` for SAML sessions (sessions from the local sign-in now correctly report `local`)
- `DELETE /api/v1/clusters/{unknown}` returns 400 rather than 404

Still thinner than a full private-cloud suite (intentionally or next):

- Embedded noVNC UI (proxy path is ready; virtctl remains supported)
- Historical Prometheus charts in the UI / alert silence (Prometheus history is used for rightsizing only)
- ClusterRole write UI (deliberate security boundary)
- SOC2 / pen-test packaging
- On-demand Velero backup (`POST /api/v1/velero/backups`) is unit-tested against a fake clientset only — no cluster in this session's environment had the Velero CRDs installed to validate it against a real one
