# Feature gaps (living)

Closed or substantially narrowed in the current tree (see CHANGELOG):

- SAML ACS sessions (`POST /api/v1/auth/saml/acs`) — the response's enveloped XML-DSig signature is verified against the pinned `AXIOM_SAML_IDP_CERT` (only the signed content is trusted, which defeats signature wrapping), and the audience (`AXIOM_SAML_ENTITY_ID`) and `NotBefore`/`NotOnOrAfter` window are enforced
- SAML `InResponseTo` and `SubjectConfirmationData` — `GET /api/v1/auth/saml/login` sends a real AuthnRequest with a random ID, recorded in a signed 5-minute `axiom_saml_req` cookie and in a single-use in-memory set; the ACS requires the signed `InResponseTo` to match both and consumes it, so a captured response cannot be replayed (not even in the same browser). Unsolicited (IdP-initiated) responses are rejected unless `AXIOM_SAML_ALLOW_IDP_INITIATED=true`. A `SubjectConfirmation` must use the bearer method, and its `SubjectConfirmationData` `Recipient` must equal this ACS URL and `NotOnOrAfter` must not have passed
- LDAP simple-bind via the local username/password form (`AXIOM_LDAP_*`)
- Operator role + safer OIDC default role env (`AXIOM_OIDC_DEFAULT_ROLE`)
- Fleet cluster register/unregister from kubeconfig (Settings → Clusters)
- HA: Helm fails when `replicaCount > 1` without `auth.sessionSecret`
- Audit ring default raised to 5000 (`AXIOM_AUDIT_RING_SIZE`)
- ConfigMap/Secret update; Velero on-demand backup; VM create/delete; PVC/Service/Ingress/Quota writes; Helm upgrade
- VM console returns proxied `wsPath` for browser VNC clients
- OIDC login validated end-to-end against a real Keycloak IdP (public client + PKCE, no client secret needed) — see `e2e/scripts/verify-sso.js`
- Enterprise write endpoints validated against a real cluster, not just the demo provider/fake clientsets — see `e2e/scripts/validate-enterprise-writes.sh`. Found and fixed one real RBAC gap: `DELETE /api/v1/vms/{ns}/{name}` was 403ing because the `zyvor-axiom` ClusterRole never granted `delete` on `kubevirt.io` VMs
- Login throttling is per client IP **and** per attempted account name (`internal/auth/ratelimit.go`); a valid login from another account can no longer reset the counter of an account being guessed. Trade-off: anyone who knows a username can lock that account for up to 5 minutes by failing logins
- OIDC ID tokens are verified against the provider's JWKS (algorithm allow-list, `kid`, signature, `iss`/`aud`/`azp`/`exp`/`sub`) and bound to the sign-in by a `nonce` cookie (`internal/api/oidc_jwks.go`)
- Browser WebSocket/EventSource auth uses single-use, 30-second tickets (`POST /api/v1/ws-ticket`) instead of credentials in the URL; the legacy `?access_token=`/`?axiom_session=`/`?api_key=` forms still work but are deprecated
- Audit log export as JSON as well as CSV
- Helm chart catalog: administrator-approved repositories, search, versions and default values, installing through the existing Helm Job; repository fetches are SSRF-guarded (no private, loopback or metadata addresses unless explicitly allowed)
- OCI chart catalog: `oci://host/path` registry namespaces as chart repositories (charts listed explicitly or through `/v2/_catalog`, versions from semver tags, metadata from the Helm config blob, values/README from the digest-verified chart layer, anonymous bearer-token flow), installing with `helm install oci://…` through the same Job and the same SSRF rules
- Fleet health: registered clusters are probed in the background and reported healthy / degraded / unreachable with latency and the last error (`GET /api/v1/fleet`, the Fleet page, the switcher dot); state changes are audited
- Fleet health history: `GET /api/v1/fleet/history` reports per-cluster uptime, failed checks, incidents and a downsampled health / latency / utilisation series over 1 h, 6 h or 24 h from the probes Axiom already runs
- Cross-cluster search: `GET /api/v1/fleet/search` finds workloads, services and namespaces by name, namespace or image across every registered cluster ("where is `payments` running?"), each through its own provider, skipping unreachable clusters and reporting failing ones
- TOTP two-factor sign-in for local accounts and the built-in admin (`POST /api/v1/auth/login`, `AXIOM_TOTP_SECRET`, enrolment and recovery codes from the user menu), with replay protection and throttling shared with passwords
- Server-side session revocation: logout ends that session, "sign out everywhere", automatic revocation on role/namespace/password changes and deletion, admin "sign out everywhere", and a configurable `AXIOM_SESSION_TTL`
- GitOps application create from the console (Ops → GitOps): Argo CD `Application`, Flux `GitRepository` + `Kustomization`, Flux `HelmRepository` + `HelmRelease`, built from typed fields with a pure YAML preview (`POST /api/v1/gitops/preview`, `POST /api/v1/gitops`), admin-only and audited
- GitOps application delete (`GET .../delete-preview`, `DELETE /api/v1/gitops/{kind}/{namespace}/{name}`): server-computed cascade (Argo CD resources finalizer, Flux `prune`, HelmRelease uninstall) with a server-enforced typed confirmation, optional removal of an unshared, Axiom-created Flux source; admin-only and audited
- GitOps application edit in place (`GET .../edit`, `POST .../edit/preview`, `PUT /api/v1/gitops/{kind}/{namespace}/{name}`): the creation form filled from the live object, a managed-field diff, and a `resourceVersion`-guarded JSON Patch of only the managed fields (everything else on the object is untouched); Flux source fields only when the source is Axiom's and unshared; admin-only and audited (field names only)
- GitOps repository credentials (`/api/v1/gitops/credentials`): write-only Argo CD repository Secrets and Flux `secretRef` Secrets (basic, token, ssh), admin-only including the listing, values never returned, logged or audited
- Read-only RBAC viewer, NetworkPolicy analysis and security-report (Trivy/PolicyReport) views
- Autoscaling beyond CPU: HPAs show every `autoscaling/v2` metric (memory, Pods, Object, External) with conditions and can be created with CPU and/or memory targets and a scale-down stabilization window; read-only VerticalPodAutoscaler recommendation and KEDA ScaledObject views (`GET /api/v1/vpas`, `GET /api/v1/scaledobjects`)
- Per-namespace monthly cost budgets (`/api/v1/cost/budgets`, admin-managed, ConfigMap `zyvor-axiom-cost-budgets`) with ok / warning / over state against the active cost source
- Actual cost from OpenCost (`AXIOM_OPENCOST_URL`): `GET /api/v1/cost` reports real allocation cost per namespace and workload with a CPU / memory / storage / network / other breakdown and the idle bucket, over a 7 / 14 / 30-day window scaled to a month, falling back to the request estimate (with a note) when OpenCost fails; budgets follow the same source
- Notifications when a cluster goes unreachable / degraded / recovers and when a cost budget reaches warning / over / back to ok, through the existing Slack / alert webhook settings (debounced, audited, shown in the Timeline; `AXIOM_BUDGET_CHECK_INTERVAL`)
- Rightsizing recommendations (`GET /api/v1/cost/rightsizing`) from Prometheus p95 CPU / p99 memory history (`AXIOM_PROMETHEUS_URL`) or, without it, a metrics.k8s.io snapshot, with per-container verdicts and monthly savings
- Rightsizing recommendations (`GET /api/v1/cost/rightsizing`) from Prometheus p95 CPU / p99 memory history (`AXIOM_PROMETHEUS_URL`) or, without it, a metrics.k8s.io snapshot, with per-container verdicts and monthly savings, and a reviewed one-container apply (`POST /api/v1/cost/rightsizing/apply`)
- LDAP group-based role mapping (`AXIOM_LDAP_ADMIN_GROUP`/`AXIOM_LDAP_VIEWER_GROUP`/`AXIOM_LDAP_GROUP_ATTR`) — only for the `AXIOM_LDAP_BASE_DN`-constructed bind form; AD-style NetBIOS/UPN binds still always get the `operator` default
- Two-factor sign-in for LDAP directory accounts: same enrolment, login, replay protection, throttling and `AXIOM_REQUIRE_MFA` policy as local accounts, records in the `zyvor-axiom-external-mfa` Secret, admin list (`GET /api/v1/users/external-mfa`) and reset

Known security limitations (reviewed, not yet fixed):

- **Two-factor sign-in does not cover SSO accounts** (they rely on the IdP's MFA), and a person who loses both their device and their recovery codes needs an administrator to reset it. A directory account's enrolment status may take up to 5 s to reach other replicas (codes themselves are always checked against the shared Secret)
- **Outstanding SAML AuthnRequests are in-memory per replica** (capped at 4096, oldest evicted first). With `replicaCount>1` the `/saml/login` redirect and the IdP's POST to `/saml/acs` must reach the same replica (session affinity), otherwise the sign-in fails with "unknown, expired or already used". The ACS URL is derived from the request (`X-Forwarded-Proto`/`X-Forwarded-Host`), so the proxy must pass the public scheme and host for the `Recipient` check to match. With `AXIOM_SAML_ALLOW_IDP_INITIATED=true`, unsolicited responses are bound only by their validity window and Recipient, not to a browser, and can be replayed within that window
- **Stream tickets are in-memory per replica.** With `replicaCount>1` a ticket is only redeemable on the replica that issued it, so WebSocket/SSE connections need session affinity (or a single replica); the login throttle counters are likewise per replica
- **The in-origin pod HTTP proxy (`/pods/{ns}/{name}/window/{port}/`) still accepts `?access_token=` for plain browser navigations** when the separate pod proxy origin is off (the default): it loads many sub-resources, so a single-use stream ticket cannot cover it. With `AXIOM_POD_PROXY_ADDR`/`AXIOM_POD_PROXY_ORIGIN` set, that route answers `410` and the UI uses single-use `window-link` tickets and a proxy-origin session cookie instead, so no console credential is put in a URL
- **Session revocation is eventually consistent across replicas.** Logout, sign-out-everywhere and account changes apply at once on the replica that handled them and on the others within `AXIOM_REVOCATION_REFRESH` (default 15 s) through the shared ConfigMap. A role change at an SSO identity provider is still only picked up at the next sign-in (an administrator can force that with "Sign out everywhere")
- **The separate pod proxy origin is opt-in and off by default.** Without `AXIOM_POD_PROXY_ADDR`/`AXIOM_POD_PROXY_ORIGIN` the pod "window" proxy still serves pod content from Axiom's own origin (CSP sandboxed into an opaque origin, cookies stripped, operator-only). With it on, pod content is isolated from the console on its own origin. Remaining with it on: every pod opened through the proxy shares that one origin (pod pages can see each other's `localStorage`, though not the HttpOnly, path-scoped session cookies); a pod's redirects or absolute links to `/…` leave its `/s/<sid>/` prefix and 404; the pod is re-resolved on the cluster the operator's console tab was viewing, so switching clusters in that tab re-targets an open session to the same-named pod there; tickets and proxy sessions are in memory per replica (session affinity needed); and a same-host, different-port setup still shares the browser's cookie jar with the console (the listener ignores console cookies, but use a separate hostname)
- **LDAP over `ldap://` is plaintext** (no StartTLS); use `ldaps://`. `AXIOM_LDAP_BIND_DN`/`AXIOM_LDAP_BIND_PASSWORD` are read but unused.
- **Default credentials**: the Helm chart and manifest default to `demo`/`demo`. Axiom logs a warning outside demo mode, and no longer advertises them on the login page, but does not refuse to start.

Known platform limitations (reviewed, not yet fixed):

- **OCI chart repositories must allow anonymous pulls.** Registry credentials are not supported (`credentialsSecret` is refused): only anonymous access, with or without the bearer-token challenge. Most hosted registries (ghcr.io, Docker Hub) do not offer `/v2/_catalog`, so their charts must be listed explicitly (at most 50 per repository); at most 500 tags per chart are read (in the registry's order), only tags that parse as semver are versions, and only the newest release's Chart.yaml is fetched, so older versions show no app version. The install Job runs `helm install oci://…` without `--plain-http`, so a plain-http registry can be browsed (with `AXIOM_HELM_ALLOW_INSECURE_REPOS`) but not installed from

- **GitOps repository credentials are not managed here.** Argo CD repository credentials are configured in Argo CD, and a Flux `secretRef` must name a Secret that already exists. Only the typed fields are supported (no multi-source Applications, ApplicationSets, Helm `valuesFrom`, or Kustomize patches)
- **VPAs and KEDA ScaledObjects can be created and deleted but not edited in place** (delete and recreate). ScaledObject triggers are limited to the allow-listed types (cpu, memory, cron, prometheus, kafka, redis lists, rabbitmq, aws-sqs-queue) and settings; anything else (other scalers, `advanced`, `fallback`, `idleReplicaCount`) must be applied as YAML. KEDA `ScaledJob`s are not shown, TriggerAuthentications are listed by name only and cannot be created (use `POST /api/v1/apply`), ClusterTriggerAuthentications are not offered, and HPA creation only offers CPU/memory Utilization targets (other metric types are displayed but must be applied as YAML)
- **GitOps editing and credentials cover the typed fields only.** Applications that use multiple Argo sources, ApplicationSets, Helm `valuesFrom`/`valuesObject`, Kustomize patches/postBuild or `chartRef` are shown read-only; a Flux source that Axiom did not create, or that other objects share, keeps its URL/revision/secretRef read-only. Repository credentials cannot be updated (rotate = delete + recreate) and cannot be read back; only Secrets with the Argo CD repository labels or Axiom's own credential labels are ever listed (arbitrary Secrets never are), and only Axiom-labelled ones can be deleted. Argo CD known hosts, GitHub App and cloud-provider credentials are not managed here
- **VPA and KEDA views are read-only.** VerticalPodAutoscalers and ScaledObjects cannot be created, edited or deleted from the console (use `POST /api/v1/apply`), KEDA `ScaledJob`s and `TriggerAuthentication`s are not shown, and HPA creation only offers CPU/memory Utilization targets (other metric types are displayed but must be applied as YAML)
- **Without OpenCost, cost figures are estimates of requested resources at flat rates** (20 USD per core, 5 USD per GiB per month), not usage and not your cloud bill. OpenCost (`AXIOM_OPENCOST_URL`) is the only source of actual cost: there is no direct cloud-billing (AWS CUR, GCP/Azure billing export) integration, OpenCost covers only the cluster Axiom starts on, and its numbers are its allocation model (on-demand list prices unless OpenCost is configured with your pricing), scaled from the window to 30 days. Rightsizing savings are always priced at the request rates
- **Rightsizing is a recommendation and is never applied automatically.** The metrics-snapshot source (no `AXIOM_PROMETHEUS_URL`) is one current sample, so its verdicts are low confidence; Prometheus covers only the cluster Axiom starts on (clusters registered later use the snapshot); requests are read from the newest running pod, so a workload scaled to zero or mid-rollout may be misjudged; Jobs, CronJobs and bare pods are not assessed, and VPA targets are not used yet
- **Fleet probing is a point-in-time overview request per cluster** (default every 30 s), and a cluster that answers slowly but successfully is still `healthy`. Health history (`GET /api/v1/fleet/history`) is in memory per replica: it is lost on restart, covers at most the last 24 h (3,000 samples per cluster), and two replicas can report different uptime. Probes use the same credentials the console uses for that cluster. Each replica probes on its own. Fleet search is a live substring match (no index, no pods, labels or other kinds) that lists every workload, service and namespace of each cluster per query, so it is rate-limited per user
- **Fleet probing is a point-in-time overview request per cluster** (default every 30 s), and a cluster that answers slowly but successfully is still `healthy`. Health history (`GET /api/v1/fleet/history`) is in memory per replica: it is lost on restart, covers at most the last 24 h (3,000 samples per cluster), and two replicas can report different uptime. Probes use the same credentials the console uses for that cluster. Each replica probes on its own, so with several replicas each one sends its own down / recovered notification
- **Notifications are best effort, not guaranteed delivery**: one attempt per channel with no retry or queue, debounce and remembered state are in memory (a restart forgets them and does not re-announce current conditions), and each replica notifies independently. The budget watcher checks only the default active cluster, and a budget that is created or changed while already over is not announced until it next crosses a threshold
- **Rightsizing recommendations are never applied automatically**: only on an explicit request for one container (`POST /api/v1/cost/rightsizing/apply`, dry run first), which changes requests only and never lowers or adds a limit. The metrics-snapshot source (no `AXIOM_PROMETHEUS_URL`) is one current sample, so its verdicts are low confidence; Prometheus covers only the cluster Axiom starts on (clusters registered later use the snapshot); requests are read from the newest running pod, so a workload scaled to zero or mid-rollout may be misjudged; Jobs, CronJobs and bare pods are not assessed, and VPA targets are not used yet
- **Fleet probing is a point-in-time overview request per cluster** (default every 30 s), and a cluster that answers slowly but successfully is still `healthy`. Health history (`GET /api/v1/fleet/history`) is in memory per replica: it is lost on restart, covers at most the last 24 h (3,000 samples per cluster), and two replicas can report different uptime. Probes use the same credentials the console uses for that cluster. Each replica probes on its own

- **Audit persistence with several replicas**: each replica keeps its own ring and `Save` is an unconditional update, so the last writer wins. (A single replica is fine; the persisted ring is now trimmed to stay under the ConfigMap size limit.)
- **Generic manifest apply uses forced server-side apply**, which still takes field ownership from Argo CD/Flux/Helm — but the apply dialog now shows a diff first and warns when another manager owns the fields. "Validate" and the real apply can still disagree for Roles/RoleBindings/ServiceAccounts because of RBAC verbs.
- **Alert dispatch has no leader election**: with `replicaCount>1` every replica posts the same Slack alert, and a flapping pod re-fires every minute.
- **Blast-radius preview and resource detail match pods by name substring** (`web` also matches `web-api-*`), and the preview's Atlas volume list can never populate (`WorkloadVolumes` is not in the Provider interface).
- **`ListSecrets` still reads every Secret with its data**, and no list call is paginated (`Limit`/`Continue`), so very large clusters are slow.
- **Interactive terminals have no idle timeout or ping/pong**; a client that vanishes without closing leaves its PTY until the pod exits. (Concurrent sessions are now capped at 64 and frames at 1 MiB.)
- **Seal NetworkPolicy names omit the workload kind**, so a Deployment and StatefulSet with the same name collide; `Approve/DenyAgentRun` do not check the current state; `GetCRDInstance`/`DeleteCRDInstance` accept built-in groups (apps, batch, rbac).

Other known gaps found by the functional test pass (see `e2e/README.md`):

- `POST /api/v1/users` maps an unknown role to `admin` (`NormalizeRole`, documented as intentional; consider fail-closed)
- A saved Slack / webhook URL cannot be cleared from the UI (the API's `*Clear` flags have no control), and the Atlas token has no UI field
- `/api/v1/session` reports `role: "Platform Admin"` for operators and `auth: "oidc"` for SAML sessions (sessions from the local sign-in now correctly report `local`)
- `DELETE /api/v1/clusters/{unknown}` returns 400 rather than 404

Still thinner than a full private-cloud suite (intentionally or next):

- Embedded noVNC UI (proxy path is ready; virtctl remains supported)
- Historical Prometheus charts in the UI / alert silence (Prometheus history is used for rightsizing only)
- ClusterRole write UI (deliberate security boundary)
- SOC2 / pen-test packaging
- On-demand Velero backup (`POST /api/v1/velero/backups`) is unit-tested against a fake clientset only — no cluster in this session's environment had the Velero CRDs installed to validate it against a real one
