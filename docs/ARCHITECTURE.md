## Provider boundary

`internal/platform/provider.go` is the contract between the API and runtime. The UX never knows whether it is connected to the deterministic lab or a real cluster — the same JSON shapes are returned in both modes. The one deliberate exception is the interactive terminal and Pod `GetResource`/YAML support, which are only registered/implemented under the `kubernetes` build tag; the frontend detects this via `GET /api/v1/realtime/capabilities` and falls back to one-shot exec in demo mode rather than pretending a PTY exists where it can't.

`DemoProvider`'s mutating methods persist their effect in the process's own in-memory state (node cordon/taint maps, per-workload rollout history, VM run state, and so on) for as long as the process runs, rather than being cosmetic no-ops — a create/delete/action in demo mode is reflected by the paired list/get call and survives a page reload, right up until the process itself restarts (demo state is never written to disk). When adding a new demo-mode mutating method, give it a real backing field/map that the corresponding read method actually consults, rather than returning a plausible-looking response and leaving the read path static — this exact class of bug (success response, no persisted state) was found and fixed across ~17 methods; see `CHANGELOG.md`.

This makes local product development possible without faking HTTP endpoints in the frontend.

## Multi-cluster (SwitchableProvider)

`cmd/zyvor-axiom/main.go` never constructs a `DemoProvider`/`KubernetesProvider` directly for the API server — it always wraps one or more of them in `platform.SwitchableProvider`, which itself implements the full `Provider` interface (`internal/platform/switchable_provider_gen.go`, one delegator method per interface method — the original generator script is no longer in the repo, so add a delegator by hand whenever `provider.go`'s interface gains a method). Every HTTP handler still calls `s.provider.Whatever(ctx, ...)` exactly as before; the switch happens one layer down, inside `SwitchableProvider.current(ctx)`.

Registration differs by mode (`internal/platform/factory_demo.go`, `factory_kubernetes.go`, `factory_multicluster.go`):

- **Demo**: `NewDemoSwitchableProvider()` registers three independent `DemoProvider` instances (`eu-west-1`/`us-east-1`/`ap-south-1`), each wrapped in `clusterLabeledProvider` so `Overview().Cluster` reports the right name per cluster without touching `DemoProvider` itself.
- **Kubernetes, in-cluster** (`rest.InClusterConfig()` succeeds — the normal ServiceAccount-based production deploy): exactly one cluster is registered, named `AXIOM_CLUSTER_NAME` or `in-cluster`. A ServiceAccount token has no concept of "other contexts", so this is the honest ceiling, not a limitation to work around.
- **Kubernetes, kubeconfig file**: every context in the file gets its own `KubernetesProvider`, registered under its context name; the file's `current-context` becomes the initially-active cluster.

**"Active cluster" is scoped per caller, not global.** `SwitchableProvider.current(ctx)` resolves the active cluster from a session key carried on `ctx` (`internal/platform/cluster_session.go`), not a single shared field. `internal/api/server.go`'s `clusterSessionMiddleware` reads the `X-Axiom-Session` request header — sent on every call by the frontend's shared axios instance (`frontend/src/lib/api.js`), which mints one random ID per browser tab via `sessionStorage` (tab-scoped, unlike `localStorage`) — and stashes it on the request context via `platform.WithClusterSession`. A request with no header (a scripted API/curl client) falls back to `"user:" + <authenticated username>` instead of one global switch. This means two tabs (or two users, or a script and a tab) can each have `POST /api/v1/clusters/{name}/activate` pointed at a different cluster simultaneously without affecting each other — `SetActive`/`ActiveName`/`Clusters` all take the same session-scoped `ctx` for consistency. Single-cluster deployments (the two Kubernetes cases above) are unaffected: with only one registered cluster there's nothing to switch between, and no session ever needs to override the default.

`GET /api/v1/clusters` / `POST /api/v1/clusters/{name}/activate` (`internal/api/clusters.go`) are the only two places that type-assert `s.provider.(*platform.SwitchableProvider)` — everything else stays cluster-agnostic.

`platform.CurrentKubernetesProvider(ctx, p)` (`internal/platform/kubernetes_lookup.go`, kubernetes-tagged) is the one place anything needs the concrete `*KubernetesProvider` behind the active cluster — used by the k8s-backed Users/Audit/Integrations stores and the interactive terminal handler. It takes `ctx` for the same session-scoping reason as `current(ctx)` above. **Anything that type-asserts `Provider` directly to `*KubernetesProvider` instead of going through this helper will silently break the moment there's more than one cluster registered** — this happened once already (see the 2026-08-28 TEST-RESULTS.md entry: it broke the interactive terminal and all Integrations persistence in production) and was fixed by routing every such call site through the shared helper instead of leaving near-duplicate type switches to drift.

## Realtime layer

`GET /api/v1/realtime/capabilities` advertises `interactiveExec` (real WebSocket PTY availability, kubernetes-build-only) and `logFollow`. `GET /api/v1/pods/{namespace}/{name}/terminal` (kubernetes build only) upgrades to a WebSocket and pipes a real PTY (`remotecommand.NewSPDYExecutor` with `TTY:true`) — the client sends raw keystrokes plus a `__resize__:WIDTHxHEIGHT` control message, and receives raw terminal output as binary WebSocket frames. The frontend's `PodTerminal.jsx` component (xterm.js) implements this protocol.

Because a plain WebSocket or EventSource can't carry a custom `Authorization` header, the SPA first calls `POST /api/v1/ws-ticket` for the exact stream path it is about to open and passes the returned single-use, 30-second ticket as `?ticket=` (`internal/auth/tickets.go`; the SPA side is `getStreamTicket` in `lib/api.js`, used by `PodTerminal.jsx`). A ticket is bound to one GET path and to the caller's resolved `Identity`, so every role and namespace check still runs when it is redeemed; only a hash of it is held in memory, and it is destroyed on first use even against the wrong path. The legacy `?access_token=` / `?axiom_session=` / `?api_key=` forms still work for scripts but answer with a `Deprecation` header. The pod HTTP proxy (`/window/{port}/`) is a plain browser navigation that loads many sub-resources, so it keeps the URL token (see `docs/GAPS.md`). OIDC/SAML sessions ride their cookie. Tickets live in each replica's memory, so a multi-replica install needs session affinity.

**Pod proxy origin.** Pod web content is hostile input. By default the window route serves it from the console's own origin behind a CSP sandbox. With `AXIOM_POD_PROXY_ADDR`/`AXIOM_POD_PROXY_ORIGIN` set, `main.go` starts a second `http.Server` (`internal/api/podproxy_origin.go`: its own handler, no CORS, 32 KiB headers, header-read and idle timeouts, HTTP/1.1, the console's TLS cert) and the in-origin route answers `410`. The console mints a link with `POST /pods/{ns}/{name}/window-link`, behind the same guard policy as the window route (`isInteractivePath` plus the `/pods` namespace check), which issues a pod-proxy ticket (`internal/auth/podproxy.go`: 256-bit, single use, 60 s, per-user cap, only its SHA-256 kept, in a store separate from the stream tickets). The browser opens `<origin>/p/<ticket>/`; redeeming it creates a proxy session whose public id goes in the path (`/s/<sid>/`) and whose separate secret goes in an HttpOnly, SameSite=Lax cookie scoped to that path on the proxy origin. Every `/s/` request needs the matching cookie, is bound to the session's user, namespace, pod and port (the pod is re-resolved through `Provider.PodProxyTarget` on the cluster the operator was viewing), and consults the console's `auth.Revocations` through the `PodProxyRevocationChecker` interface, so a user cut-off after the ticket was minted kills the session. Both routes share one proxy core (`servePodProxy` in `window.go`) that strips the caller's credentials and the pod's `Set-Cookie`; only the response policy differs. The proxy origin is isolated from the console, so its sandbox keeps `allow-same-origin`, which the SameSite cookie needs on sub-resource requests. As a result, pods opened through it share that one origin with each other; HttpOnly path-scoped cookies, unguessable session ids, refused service workers and stripped `Service-Worker-Allowed`/`Clear-Site-Data` limit what one pod's page can do to another's session. The listener never reads the console's cookie or credentials, because cookies are not port-isolated.

## Generic apply and the CRD browser

`ApplyManifest` (`internal/platform/ops_kubernetes.go`) reuses `ValidateManifest`'s exact parse-and-discover path — YAML/JSON → `unstructured.Unstructured` → GVK→GVR via `restmapper.NewDeferredDiscoveryRESTMapper` — but replaces the dry-run `Create` with a real `Patch(types.ApplyPatchType, FieldManager: "zyvor-axiom")`. This is the one endpoint that lets an operator apply an arbitrary manifest through Axiom instead of only the handful of typed resources every other endpoint models explicitly; the frontend's editable-YAML tabs (Workload/Pod detail) and the NetworkPolicy "Create via YAML" flow all funnel through it. A manifest holding several YAML documents (`---`) is **rejected** by both validate and apply (one object at a time) rather than applying only the first. It only exists under the `kubernetes` build tag — the demo provider returns a fixed "not available in demo mode" result rather than simulating a fake apply.

The CRD browser (`ListCRDs`/`ListCRDInstances`/`GetCRDInstance`) is a separate, narrower mechanism: `ListCRDs` reads `apiextensions.k8s.io` CustomResourceDefinition objects (a well-known GVR, no extra `k8s.io/apiextensions-apiserver` dependency needed), while `ListCRDInstances`/`GetCRDInstance` build a GVR directly from a CRD's own `.spec.names.plural` and hit it with the dynamic client — no restmapper round-trip needed, since the CRD object already carries everything required. Listing CRD *definitions* only needs the `apiextensions.k8s.io` RBAC grant Axiom always ships with; listing/getting CRD *instances* needs the ServiceAccount to actually have RBAC for that specific group, which `deploy/k8s/rbac.yaml` grants as a curated per-group allowlist, not a wildcard `list` on everything. Browsing an ungranted CRD's instances surfaces the real Kubernetes `403 Forbidden` message to the frontend rather than a misleading empty list — see `CustomResources.jsx`'s `instancesError` state, which distinguishes "genuinely empty" from "you don't have RBAC for this."

Per-pod metrics (`GetPodMetrics`) reuse the same raw `AbsPath("/apis/metrics.k8s.io/v1beta1/namespaces/{ns}/pods/{name}")` REST-on-the-existing-client trick as node metrics, plus an in-memory per-pod ring buffer (`podMetricsHist`, keyed `namespace/name`, capped at 48 samples with ≥20s spacing) so the frontend can render a short rolling sparkline without a real time-series backend. Entries are evicted once the map exceeds 500 pods (mirrors `RateLimiter.sweepLocked` in `internal/auth/ratelimit.go`) so a long-running process doesn't accumulate unbounded per-pod history. This is explicitly a live rolling window, not historical Prometheus data — the UI says so.

## Node metrics, taints, and pod scheduling diagnosis

`GetNodeMetrics` reuses the exact per-pod metrics ring buffer (`recordPodMetric`/`podMetricPoints`) rather than a second buffer, keyed `"node:<name>"` — node names never contain a `/`, so this can't collide with a pod key (`"namespace/name"`). `AddTaint`/`RemoveTaint` follow the same get-mutate-`Nodes().Update` shape as `Cordon`.

`DiagnosePod` is read/aggregation-only: it correlates the pod's `PodScheduled` condition, matching Warning-type Events (via a field selector on `involvedObject.name`/`.kind`), and container `Waiting` reasons into one plain-English diagnosis — no new Kubernetes API dependency beyond what `ListPods`/`ListEvents` already use, just a smarter synthesis of data already being fetched elsewhere. Surfaced as an automatic banner on Pod detail (not a tab a user has to think to click) whenever the pod isn't cleanly `Running`/`Succeeded`.

## Fleet health

`SwitchableProvider` also owns the fleet prober (`internal/platform/fleet.go`). `ProbeAll` asks every registered cluster's own `Provider` (never the session-scoped active one) for its `Overview` under a per-probe timeout, with bounded concurrency, and caches a `ClusterHealth` per cluster: the state (`healthy` / `degraded` when nodes are not ready or the cluster reports a problem / `unreachable` when the probe errors or times out), latency, the flattened error, when the state last changed, and the headline numbers the Fleet page shows. `StartFleetProber` runs it on an interval (`AXIOM_FLEET_PROBE_INTERVAL`, started from `main.go`); a cluster registered at runtime is probed at once; `RefreshFleet` backs the "Check now" button and refuses to run more than once every 3 s. State transitions are written to the audit log. A cluster that was reachable must fail two probes in a row before it is called unreachable (one slow overview is not an outage), and warning events alone never degrade it (the Kubernetes provider's "Attention" status is ignored; only unready nodes or an explicitly unhealthy status do). `Fleet()` assembles the roll-up served by `GET /api/v1/fleet` and probes any cluster that has never been probed, so the answer is complete even with background probing off. `ClusterInfo` (the switcher list) carries the same state, and the top-bar chip shows a green / orange / red dot for the *active* cluster. In demo mode `AXIOM_DEMO_FLEET_DOWN` / `AXIOM_DEMO_FLEET_DEGRADED` wrap a demo cluster in `simulatedClusterProvider` so the unhappy states can be tested without a broken cluster.

Fleet history (`internal/platform/fleet_history.go`, `GET /api/v1/fleet/history`) is a per-cluster slice of samples in `fleetState`, appended by `probe` after the hysteresis decision (the swallowed-failure branch records the held state, flagged as a failed check) and pruned on every append to 24 h / 3,000 samples. `recordHistory` holds `sp.mu` (read) across the "still registered?" check and the append, in the same `sp.mu` → `st.mu` order as `Unregister` → `forgetHealth`, so a probe finishing after an unregister cannot resurrect the cluster's history. `FleetHistory` copies the window's samples under the lock and computes the downsampled series, time-weighted uptime and merged incidents outside it, all pure functions. It is memory only and per replica; `seedFleetHistoryForDemo` (behind `AXIOM_DEMO_FLEET_HISTORY_SEED`) backfills the demo clusters for tests.

Fleet search (`internal/platform/fleet_search.go`, `GET /api/v1/fleet/search`) reuses that machinery: `SearchFleet` walks the registered entries (not the session-scoped active provider), probes any never-probed cluster first, skips clusters whose cached state is `unreachable`, and calls `ListWorkloads("all")` / `ListServices("all")` / `ListNamespaces` on each remaining cluster's own provider with the probe concurrency bound and a 5 s per-cluster timeout. The list calls run in their own goroutine so a provider that ignores its context still cannot hold the search; failures are reported per cluster with credentials stripped from URLs. Matches are ranked (exact name, prefix, contains, namespace/image) and limited after a global sort. The handler (`internal/api/fleet_search.go`) validates the query and applies a per-user limit of 20 searches per 10 s, because each search lists every cluster's objects. No Provider methods were added.

## Autoscaling beyond CPU

HPAs are read and created through `autoscaling/v2` (`internal/platform/autoscaling_kubernetes.go`), so every metric type is rendered (`HPAMetric`: Resource, ContainerResource, Pods, Object, External with target and current as display strings) together with the status conditions, desired replicas, last scale time and whether a `behavior` block is set. `CreateHPA` validates in one shared, build-tag-free function (`normalizeCreateHPARequest` in `autoscaling.go`) used by both providers, writes one Resource Utilization metric per CPU/memory target and an optional scale-down stabilization window. The VPA and KEDA views are read-only dynamic-client lists (`ListVPAs` tries `autoscaling.k8s.io/v1` then `v1beta2`; `ListScaledObjects` reads `keda.sh/v1alpha1` and joins the KEDA-owned HPA for the live replica count) that report `installed:false` instead of an error when the CRD is absent. ScaledObject triggers are reduced to type and an identifier-only name: trigger metadata and `authenticationRef` never leave the provider. Types are in `types_autoscaling.go`, routes in `internal/api/autoscaling.go`. VPAs and ScaledObjects are edited in place with the GitOps edit's design (`autoscaling_edit.go`, pure; `autoscaling_edit_kubernetes.go`, `autoscaling_edit_demo.go`): the typed create fields are read back (anything the model cannot represent, and any credential-looking trigger setting, makes the object `editable:false`), the edit is validated by `buildVPA` / `buildScaledObject`, and only the managed fields are written as a JSON Patch that first `test`s `metadata.resourceVersion`.

VPAs and ScaledObjects are created the way GitOps applications are: a typed request (`VPACreateRequest`, `ScaledObjectCreateRequest`) is validated and rendered field by field in the pure, build-tag-free `autoscaling_build.go` (the preview handlers call `PreviewVPA` / `PreviewScaledObject` directly, so preview needs no cluster), which also holds the closed KEDA trigger allow-list: per type, the required and optional setting keys, a validator per value, whether `authenticationRef` is forbidden/optional/required, and a credential-key and URL-userinfo screen so secrets can only arrive as the name of a TriggerAuthentication. `autoscaling_create_kubernetes.go` resolves the served version by discovery (VPA `v1` then `v1beta2`; KEDA `v1alpha1`; `422` when absent), checks the TriggerAuthentications exist, lists the namespace's HPAs for the conflict warnings, and creates one object with the dynamic client (`409` on exists). The demo keeps VPAs and ScaledObjects in an in-memory store seeded from the read-side demo data (`autoscaling_create_demo.go`). Because the namespace of a create is in the body, the guard lets those four `POST` routes past its namespace check (`auth.isBodyNamespaceRoute`) and the handlers call `auth.NamespaceAllowed` on the body's namespace first.

## Helm chart catalog

`internal/platform/helmrepo.go` backs Ops → Helm's repository browser. `HelmCatalog` combines a `HelmRepoStore` (in memory in demo mode, ConfigMap `zyvor-axiom-helm-repos` in the kubernetes build — `helmrepo_k8s.go` / `helmrepo_stub.go`, opened from `main.go` and passed in through `api.AuthOptions.HelmRepoStore`) with a per-repository cache of the parsed `index.yaml` (10 min TTL, single-flight per repository, stale copy kept with the error when a refresh fails). All network access goes through `HelmFetcher`: an `http.Client` with no proxy, no cookie jar, a 15 s timeout and a custom `DialContext` that resolves the host itself, refuses the connection if any resolved address is non-public (unless `AXIOM_HELM_ALLOW_PRIVATE_REPOS`) and then dials that validated IP — so there is no second DNS lookup to rebind — with a `net.Dialer.Control` re-check on the socket address as a second line. `CheckRedirect` re-applies the static URL rules to every hop (at most 3). Chart archive URLs from an index are treated as untrusted input and pass the same rules. `values.yaml` and `README.md` are read straight out of the downloaded `.tgz` in memory (exact `<chart>/…` names, regular files only, size-capped); nothing is extracted to disk. HTTP routes are in `internal/api/helm_catalog.go`; the admin-only rule for repository writes is `internal/auth/policy_helm.go`. Installing still goes through the existing `helm install --repo` Job.

OCI repositories (`kind: "oci"`, `oci://host/path`) are handled by `internal/platform/helmoci.go` (pure stdlib, both builds), which builds the same in-memory `helmIndex` the index path produces, so the cache, single flight, stale-on-error, search, detail and the 20-repository cap are shared unchanged. A `helmOCIClient` per fetch pings `GET /v2/` (https, falling back to http only with `AXIOM_HELM_ALLOW_INSECURE_REPOS`), lists charts from the repository's explicit `charts` or `/v2/_catalog`, then per chart (4 at a time) pages through `tags/list`, keeps semver tags, and reads the newest release's manifest and Helm config blob (Chart.yaml as JSON) — the chart layer is only downloaded for values/README and goes through `readHelmChartArchive`. Every request is a `HelmFetcher` request, so dial-time address checks and redirect re-validation apply to registry, blob-storage redirects and the bearer realm alike; a realm on another host uses a second fetcher with the strict public-https policy. A 401 bearer challenge is answered once with an anonymous token per scope (cached for that fetch only); blobs are sha256-verified while they stream. An OCI install passes the catalog's `ref` as `InstallHelmRequest.OCIRef`, and the Job runs `helm install <release> oci://…` with literal args and no `--repo`.

## Gateway API and admission webhooks

`ListGateways` mirrors `ListGitOps`'s CRD-missing-tolerant dynamic-client pattern: it tries `gateway.networking.k8s.io/v1` first, falls back to `v1beta1`, and returns an empty list (not an error) if neither CRD is installed — most clusters don't have Gateway API yet. `ListAdmissionWebhooks` is simpler: `admissionregistration.k8s.io/v1` is a stable built-in API, so it uses the typed clientset directly (`k.client.AdmissionregistrationV1()`), the same shape as `ListRBAC`, with no CRD-missing handling needed.

## Change safety, graph, timeline and health check

These v0.4 features are all read paths over the existing `Provider`, plus one dry-run write.

- **Diff before apply.** `POST /api/v1/apply/diff` calls `DiffManifest` (`internal/platform/diff*.go`), which runs server-side apply with `dryRun=All` and returns live vs. proposed per object. Secret `data` is masked on both sides, and `managedFields` managers other than `zyvor-axiom` (Argo CD, Flux, Helm) are reported so the UI can warn that a forced apply takes their fields. The apply dialog and the Workload/Pod YAML tabs enable Apply only after the diff has been shown (`DiffReview.jsx`).
- **Relationship graph.** `GET /api/v1/graph/{namespace}/{kind}/{name}` (`graph_kubernetes.go`) walks owner references and selectors to the Services, Ingresses, HPAs, ReplicaSets/Pods and mounted PVC/ConfigMap/Secret *names* — never values. `ResourceGraph.jsx` draws it as keyboard-focusable SVG nodes.
- **Timeline.** `GET /api/v1/timeline` merges Kubernetes events, the Axiom audit ring, alert warnings and rollout revision times into one list (`internal/platform/timeline.go`, `internal/api/timeline.go`). Namespace-restricted identities only receive entries for their namespaces.
- **Health check.** `GET /api/v1/diagnose` runs deterministic analyzers (`internal/platform/diagnose*.go`: pod status, Service endpoints, Pending PVCs, Ingress backends, HPA targets, node pressure), each emitting a severity and a suggested fix. No model is involved.
- **Multi-pod logs, debug container, node shell.** `GET /workloads/{ns}/{kind}/{name}/logs` merges the logs of a workload's pods. `POST /pods/{ns}/{name}/debug` adds an ephemeral container (`AXIOM_DEBUG_IMAGE`, default busybox) and the existing terminal attaches to it. The node shell is **off by default** (`AXIOM_ENABLE_NODE_SHELL=true`), admin-only and audited; it runs a short-lived privileged pod pinned to the node and removes it when the session ends.

## Security views and the AI assistant

- **RBAC viewer.** `/api/v1/rbac/subjects`, `/subjects/{kind}/{name}` and `/who-can` (`internal/platform/rbac_view.go`) resolve bindings through their Roles into effective permissions. They enumerate the whole access graph, so viewers and namespace-restricted accounts get `403` and operators can read but not write (`internal/auth/rbac_view.go`). A who-can answer needs a complete snapshot; if any list fails the request fails rather than answering from partial data.
- **NetworkPolicy analysis and security reports.** `/networking/policies/{ns}/analysis` computes, per pod, whether it is isolated and which peers and ports are allowed. `/api/v1/security/reports` aggregates Trivy-operator `VulnerabilityReport` / `ConfigAuditReport` and `wgpolicyk8s.io` `PolicyReport` objects through the dynamic client when their CRDs exist, and reports "not installed" otherwise.
- **OIDC hardening.** `internal/api/oidc_jwks.go` verifies the ID token against the provider's JWKS (algorithm allow-list, `kid`, signature, `iss`/`aud`/`azp`/`exp`/`sub`) and binds it to the sign-in with a `nonce` cookie. Login throttling is per client IP and per attempted account (`internal/auth/ratelimit.go`).
- **AI assistant (opt-in).** Disabled until an admin configures a provider in Settings (OpenAI-compatible, Anthropic or local Ollama); the API key lives in the integrations Secret and is never returned. `POST /api/v1/ai/explain` builds its context only from what the caller may already see (events, health findings, container statuses, a log tail), passes it through the redactor in `internal/platform/ai_redact.go` (no Secret/ConfigMap values or env values; IPs and hostnames too when redaction is on), and the UI shows the redacted payload before sending. The call is read-only, rate-limited per user, and audited as `ai.explain` with the target only — the prompt and answer are not stored.

## RBAC write boundary

`CreateRole`/`DeleteRole`/`CreateRoleBinding`/`DeleteRoleBinding` are deliberately scoped to namespaced `Role`/`RoleBinding` only — `ClusterRole`/`ClusterRoleBinding` have no corresponding write methods and stay read-only via `ListRBAC`. This is a conscious security boundary, not an oversight: a UI path to create cluster-scoped roles is a materially bigger privilege-escalation surface than a namespace-scoped one, and every other write feature in this app is namespace-scoped already. `deploy/k8s/rbac.yaml` reflects this split explicitly — the ServiceAccount's own `rbac.authorization.k8s.io` grant is `get/list/watch` for `clusterroles`/`clusterrolebindings` but `get/list/watch/create/delete` for `roles`/`rolebindings`.

## GitOps sync and Helm install (dynamic client, no SDKs)

`TriggerGitOpsSync` branches by the `Kind` already known from `ListGitOps`: Flux Kustomization/HelmRelease get their `reconcile.fluxcd.io/requestedAt` annotation bumped to `time.Now()` (the same force-reconcile convention `flux reconcile` uses); Argo Application gets its top-level `operation.sync` field set (the same mechanism `argocd app sync` uses). Both are a JSON merge patch via the dynamic client (`patchFirstGVR`, trying each fallback GVR in turn and tolerating a missing CRD) — consistent with how Flux/Argo/Velero are accessed everywhere else in this codebase; there's no SDK for either engine.

`InstallHelmChart` reuses the exact "launch a `batchv1.Job` running `alpine/helm`" mechanism `HelmUninstall`/`HelmRollback` already use, rather than adding a Helm Go SDK dependency. It runs `helm install --repo <url>` (fetching the chart directly from the repo's index) instead of a separate `helm repo add && helm install` shell pipeline, so every argument is a literal element of the Job's `Command` slice with no shell interpolation of user input anywhere — no command-injection surface regardless of what characters are in the release/chart name or repo URL. Optional values YAML is mounted from a ConfigMap (`/values/values.yaml`), not passed as an arg. There is no chart-repo browsing or index parsing — the caller supplies a repo URL and chart name directly, the same as `helm install --repo` on the CLI; a searchable chart catalog would be a separate, larger feature.

The install path does **not** pass `--wait` (unlike uninstall/rollback, which rely on it) — install is already framed to the caller as "started" rather than a synchronous result, and confirmed by live testing against a real cluster, `--wait` needs RBAC read on `apps/replicasets` to poll rollout status, and even applying a Deployment-backed chart at all (not just waiting on it) needs that same `replicasets` read — `deploy/k8s/rbac.yaml` grants it read-only, alongside the existing `deployments`/`statefulsets` write grant.

## GitOps application creation (typed builders, version fallback, rollback)

`POST /api/v1/gitops` never accepts YAML from the client. `internal/platform/gitops_build.go` (pure, both build modes) validates a typed `GitOpsCreateRequest` and assembles each object field by field, so a request cannot inject other kinds, finalizers, annotations, or spec fields the form does not show; repository URLs with credentials are refused outright so a secret is never written into a CR (Flux takes a `secretRef` name, Argo CD keeps repository credentials itself). The same builder backs `POST /api/v1/gitops/preview`, which renders with the newest API version of each kind and never calls the cluster. On create, `KubernetesProvider.CreateGitOpsApp` first resolves every object's version through discovery from candidate lists next to the list/sync ones (`fluxGitRepositoryGVRs`, `fluxHelmRepositoryGVRs`, `fluxKustomizationGVRs`, `fluxHelmReleaseGVRs`, `argoAppGVRs`, newest first), so a cluster on older Flux APIs works and a missing CRD fails with `422` before anything is written. Objects are then created in order (source first) with field manager `zyvor-axiom`; if a later one fails, the objects this request already created are deleted again (UID precondition) and the error reports both facts. Axiom never adds the Argo CD `resources-finalizer`, and labels everything it creates `app.kubernetes.io/managed-by: zyvor-axiom`.

**Deletion (`gitops_delete.go`, pure; `gitops_delete_kubernetes.go`, `gitops_delete_demo.go`).** Deleting a GitOps object is dangerous because the *controller* may cascade: an Argo CD Application carrying `resources-finalizer.argocd.argoproj.io` (or a `/…` variant) deletes every resource it manages, a Flux Kustomization with `spec.prune: true` garbage-collects its inventory, and a Flux HelmRelease uninstalls its release unless `spec.suspend` is true. `buildGitOpsDeletePreview` applies exactly these rules to the live object and also reports the Flux source and every other Kustomization/HelmRelease that references it. The DELETE handler does not trust the preview the UI showed: the provider re-reads the object and recomputes the cascade at delete time (a finalizer may have been added in between), and a cascading delete is refused with `400` unless `?confirm=` equals the object name exactly — the typed confirmation is enforced server-side so a buggy or scripted client cannot skip it. The object is deleted with default propagation and a UID precondition; Axiom does not try to influence the cascade with propagation policies, because the finalizer semantics belong to the controller. `removeSource=true` deletes the Flux source only after the application, only when no other object references it and only when it carries the managed-by label (all checked before the first delete); a failed source delete is reported as a warning, since the application is already gone.

**Editing and repository credentials (`gitops_edit.go`, `gitops_repocreds.go`, pure; `*_kubernetes.go`, `*_demo.go`).** `GET …/edit` reads the typed creation fields back out of the live object; anything the typed model cannot represent (multiple Argo sources, `valuesFrom`, Kustomize patches/postBuild, `chartRef`, an ApplicationSet owner, …) makes it `editable:false` instead of being silently dropped. An edit is validated by the same `buildGitOps` as creation, and the rendered object supplies the target value of each *managed* field; the patch is a JSON Patch built only from those paths, so annotations, finalizers, status and unknown spec keys are never touched (a merge patch could neither replace Helm `values` wholesale nor express a removal inside them). Concurrency is guarded twice: the provider re-reads the object and refuses a `resourceVersion` different from the one the editor loaded (`409`), and the patch's first operation `test`s `metadata.resourceVersion`, so a change between that read and the write also fails. A Flux source is patched (first) only when it carries the managed-by label and is unshared — otherwise its fields are read-only, the same rule `removeSource` uses. Repository credentials are write-only Secrets: values go from the request body into the Secret and nowhere else (no read path, generic decode errors, the body buffer and rendered data are zeroed after use, the request type's `String()` redacts, audit entries carry names and the auth type only); listing is limited to Argo CD's repository labels and Axiom's own credential labels, never arbitrary Secrets; delete requires Axiom's labels; there is no update (rotate = delete + create). The existing ClusterRole already grants Secrets cluster-wide, so no RBAC change was needed.

## Per-workload cost and multi-tab terminal

`EstimateCost`'s existing per-pod, per-container CPU/memory-request accumulation loop (already grouping into `byNS` for the "by namespace" breakdown) gained a second `byWorkload` accumulator populated in the same pass — no extra Kubernetes API calls. The workload key is derived from the pod's controlling owner reference (`workloadOwnerForPod`); a `ReplicaSet` owner has its pod-template-hash suffix stripped (`strings.LastIndex(name, "-")`), since Deployments always name their managed ReplicaSets `<name>-<hash>` — this rolls pods up to the Deployment they actually belong to (`checkout`) rather than the ReplicaSet's generated name (`checkout-7f7fc496b4`), confirmed against 72 real workloads on the live cluster. A bare Pod with no controller owner falls back to its own name.

**Budgets and rightsizing.** Budgets (`internal/platform/cost_budgets.go`, pure) are compared with `EstimateCost` on every read; a `CostBudgetStore` keeps them in memory (demo) or in ConfigMap `zyvor-axiom-cost-budgets` (`cost_budgets_k8s.go`, same load/mutate-with-conflict-retry pattern as the Helm repository store) and is handed to the API through `api.AuthOptions.CostBudgetStore`. Rightsizing (`Provider.ListRightsizing`) is split so all the logic compiles in both builds: `cost_rightsizing.go` holds the recommender (headroom, rounding, verdicts, deltas priced with the same rate constants as `EstimateCost`) and the `rightsizingUsageSource` seam; `prometheus.go` holds a bounded Prometheus client (no proxy, 10 s, 8 MiB, same-host redirects only, URL/token kept out of errors) and the PromQL builders (label values quoted with Go/PromQL escaping). `cost_rightsizing_kubernetes.go` gathers per-container requests from the newest running pod of each Deployment / StatefulSet / DaemonSet, resolves pod samples to workloads (owner references, then pod-name suffix rules for pods that are gone) and tries Prometheus (when `ConfigurePrometheus` attached a client to the startup cluster's provider) before a metrics.k8s.io snapshot; a source that errors or returns nothing becomes a note and the next one is used. A VPA source would be a third `rightsizingUsageSource`.

**Actual cost (OpenCost).** `GET /cost` and the budgets go through `ActiveCost` (`internal/platform/cost_opencost.go`, both builds) rather than calling `Provider.EstimateCost` directly. It always computes the request estimate (for the `cpuCores`/`memoryGi` columns and as the fallback), then looks for a `costAllocationSource` on the cluster the context resolves to: `ConfigureOpenCost` (from `main.go`, like `ConfigurePrometheus`) attaches an `OpenCostClient` to the startup cluster's `KubernetesProvider`, and in demo mode `AXIOM_DEMO_OPENCOST=true` makes `DemoProvider` answer with fixed data. The client reuses Prometheus' bounded HTTP client (`newOperatorHTTPClient`), runs one `/allocation/compute` query per window (aggregated by namespace, controller kind and controller; namespace totals are summed from it), parses tolerantly (unknown fields ignored, a malformed row skipped, non-finite numbers as 0, `__idle__` / `__unmounted__` / `__unallocated__` kept apart), and caches per window for 60 s behind a single flight whose fetch is detached from the first caller's cancellation. `costFromAllocations` scales to 30 days by the minutes the data covers and merges the request columns. Any failure yields the estimate plus a note built only from the client's own sanitised messages. No Provider method was added.

**Applying rightsizing.** `Provider.ApplyRightsizing` (`cost_rightsizing_apply.go`, pure: validation, the stale-view check, the change plan and the patch body) recomputes the recommendation server-side for the one named container through the same gathering and source choice as the report (`recommendOneContainer`), so a client can never write numbers of its own. The plan only moves `requests` of the chosen resources to the recommendation and never lowers or adds a limit — an existing limit below the new request is raised to it and reported. When the caller passes the `observed` requests it saw and they no longer match the live ones, the apply is refused (`409`), so nobody applies a recommendation computed against a view that changed under them. `cost_rightsizing_apply_kubernetes.go` sends one strategic-merge patch on the workload (field manager `zyvor-axiom`) and lets the controller roll it; the demo provider keeps applied values in memory per provider.

The multi-tab terminal (`PodDetail.jsx`'s `TerminalSessions`) requires no backend changes at all: `ExecWS` already builds a fresh `remotecommand.NewSPDYExecutor` and a fresh `*websocket.Conn` per request, with no shared per-connection state beyond a presence counter (`internal/platform/track.go`) — confirmed by opening two simultaneous raw WebSocket connections to the same real pod and running different commands on each with zero cross-talk. `TerminalSessions` is a thin array-of-`{id}` React state wrapper rendering nested shadcn `Tabs`, each mounting its own keyed `<PodTerminal>` instance; `PodTerminal.jsx` itself is unchanged, since it already owns a fully isolated xterm+WebSocket pair per mount.

## Users and RBAC

`internal/platform/users.go` defines `User`/`UserStore`/`UserHub`; passwords are bcrypt-hashed (`golang.org/x/crypto/bcrypt`), never stored or returned in cleartext. `UserHub` keeps an in-memory cache loaded from the store at startup so every request authenticates without a store round-trip. Persistence mirrors the Integrations pattern: `MemoryUserStore` in demo, `K8sUserStore` in production (a single JSON blob under `zyvor-axiom-users` Secret's `users.json` key, in the same namespace as everything else Axiom owns). `UserHub.UpdateRole`/`ResetPassword`/`UpdateNamespaces` let an existing account be edited in place rather than requiring delete-and-recreate.

`UserHub` implements `auth.UserAuthenticator` (`Authenticate(username, password) (role string, namespaces []string, ok bool)`), which `internal/auth.Guard` consults after the single env-configured account fails to match. `Guard.Middleware` resolves a full `Identity{User, Role, Namespaces}` for every request — from the session cookie (OIDC), the API key, the env account, or a local `UserHub` account — and:

1. Rejects any `viewer`-role identity attempting a mutating HTTP verb (`POST`/`PUT`/`PATCH`/`DELETE`) with `403`, before the request reaches routing.
2. For an identity with a non-empty `Namespaces` (only ever set on local viewer accounts — `platform.normalizeNamespaces` forces it to `nil` for any admin), checks the request's namespace against the allowed set via `namespaceOfRequest` — reading `?namespace=` when present, or the path segment following a fixed allowlist of namespaced-resource prefixes (`namespacedResourcePrefixes`) otherwise. A request that resolves to no namespace or `all` is treated as cross-namespace and blocked, since that's the exact leak this exists to prevent.

Both checks are the only enforcement points; no individual handler checks role or namespace. OIDC sessions get a role from `internal/api/oidc.go`'s `resolveOIDCRole`, which reads the ID token's groups claim (`AXIOM_OIDC_GROUPS_CLAIM`, default `groups`) and maps it against `AXIOM_OIDC_ADMIN_GROUP`/`AXIOM_OIDC_VIEWER_GROUP` — unset (the default), every OIDC session stays admin, unchanged from before this existed. OIDC sessions never carry a namespace restriction in this pass; that's local-viewer-only.

The audit trail (`internal/platform/audit.go`) persists the same way: an optional `AuditStore` (`SetAuditStore`, called once at startup) backs the existing in-memory ring, so `RecordAxiomAudit`/`ListAxiomAudit` call sites never changed — in kubernetes mode a `zyvor-axiom-audit` ConfigMap holds the last 200 entries and survives restarts; demo mode stays purely in-memory.

### Two-factor sign-in and session revocation

HTTP Basic carries credentials on every request and has no place for a second factor, so an account with two-factor sign-in is refused Basic (`Guard.authorizeDetail` returns an identity flagged `mfaPending`, which the middleware turns into `401` plus `X-Axiom-MFA: required`) and signs in through `POST /api/v1/auth/login` instead. That endpoint is served by the guard itself (`internal/auth/login.go`) ahead of authentication so password and code guesses go through the same per-IP and per-account throttles; on success it issues a signed session (`Issuer: "local"`) as a cookie and a `Bearer axiom.…` token. TOTP (`internal/auth/totp.go`, standard library only) accepts one step of drift and refuses a step at or before the last one used; the user's `MFALastStep`, hashed recovery codes and secret live in the same Secret as the password hash (`internal/platform/users_mfa.go`), serialised by a mutex, and a verification whose new state cannot be persisted fails rather than leave a code replayable.

Sessions from the local sign-in are not trusted for their claims: `identityFromSession` re-resolves role and namespaces from the live account (`UserLookup`), so a role change, a new namespace restriction or a deleted account applies on the next request, and a namespace-restricted viewer keeps their restriction when signed in with MFA. `auth.Revocations` (`internal/auth/revocation.go`) is the server-side memory that can end a stateless token early: individually revoked session IDs and a per-user cut-off in Unix milliseconds that revokes everything issued at or before it. `UserHub` calls a hook on every change that should end sessions (password, role, namespaces, MFA, delete). The snapshot is persisted through `auth.RevocationStore` (a `zyvor-axiom-revocations` ConfigMap in kubernetes mode, memory in demo) and is small and bounded. Each replica keeps its own copy and shares it: `persist` does a read-modify-write through the optional `auth.MergingRevocationStore` (the ConfigMap store's `Merge` updates with the resourceVersion it read and retries on `409 Conflict`; stores without it fall back to Load + Save), and `Revocations.StartRefresh` (started from `main.go`, `AXIOM_REVOCATION_REFRESH`, default 15 s) re-reads the store and merges. Merging is a union of revoked IDs with the later per-user cut-off winning, so it never un-revokes and never drops a local entry; pruning is the same as on every change.

The require-MFA policy (`AXIOM_REQUIRE_MFA`, `auth.MFAPolicy` on `Guard.RequireMFA`, `internal/auth/mfa_policy.go`) is enforced centrally in `Guard.Middleware`, like the viewer write-block, not in handlers. Each `Identity` records how its credentials are managed (local account, built-in env admin, directory/LDAP, or external: SSO, API key); only local and directory accounts whose role the policy covers and for which `MFAProvider.MFAEnrolled` is false are confined to the enrolment and sign-out routes. The built-in env admin never is: with `AXIOM_TOTP_SECRET` it already needs a code, and without it it is exempt as break-glass. `Guard.MFAState` backs the `mfa` object of `GET /api/v1/session`.

Directory (LDAP) accounts get the same second factor without a local account. Their records live in `platform.ExternalMFAStore` (`internal/platform/external_mfa.go`; the `zyvor-axiom-external-mfa` Secret in kubernetes mode via `external_mfa_k8s.go`, memory otherwise), keyed by lower-cased directory username, and share the TOTP/recovery/replay state machine with `UserHub` (`mfaFactor` in `internal/platform/mfa_factor.go`). The Secret is written read-modify-write with the resourceVersion it read and retried on conflict; every verification re-reads it, so a code used on one replica is refused on another, while `MFAEnrolled` reads through a 5 s cache. `Guard.ExternalMFA` is consulted only on the LDAP branch of `authenticatePassword`, after the bind succeeded, and only when no local account has that name (`ldapMFAProvider`: local first, as for passwords). The identity is tagged as directory-sourced (`Identity.ViaLDAP`), the login endpoint issues `Issuer: "ldap"` sessions, and `identityFromSession` accepts them with the role mapped at bind time rather than re-resolving it (there is nothing local to look up; a directory change applies at the next sign-in, and revocation ends them like any session). The API's `caller()` maps such identities to `callerLDAP`, which the self-service MFA handlers serve from the external store and `Guard.VerifyPassword` checks with a bind. The require-MFA policy applies to them only when such a store is configured (the server always configures one), so it can always be met.

## Alert notifications

`internal/platform/notify.go`'s `RunAlertDispatcher` runs as a background goroutine (started once in `main.go`, alongside the HTTP server) that polls `Provider.ListAlerts` every 60s. When `Integrations.NotifyOnWarnings` is true, any Warning event newer than the last-seen watermark is forwarded to `SlackWebhookURL` and/or `AlertWebhookURL` via a plain `POST` (Slack's `{"text":...}` shape, or a structured JSON payload for generic webhooks). Dispatch errors are logged, never fatal — a broken webhook URL can't take down the API server. The one-shot "Test" buttons in Settings call the same `SendSlackMessage`/`SendAlertWebhook` functions directly.

Axiom-level notifications go through the `Notifier` seam (`internal/platform/notifier.go`): `NewHubNotifier(hub)` formats a `Notification` (title, one-line detail with URLs reduced to scheme://host, an Axiom-relative path, the audit action as `kind`) and hands it to the dispatcher's `deliver`, so it uses the same channels, the same `notifyOnWarnings` switch and the same URL-scrubbing sender; it is a no-op when notifications are off. Two producers use it, both through `notifyGate` (no repeat of the same state for a subject within 10 minutes; a recovery always follows an announced problem): the fleet prober, on the transitions it already audits (`SetFleetNotifier`, called synchronously from `probe`), and the budget watcher (`internal/platform/cost_budget_watch.go`, `StartBudgetWatcher` from `main.go`), which runs `CostBudgetReportFor` — the function behind `GET /cost/budgets` — with a session-less context (the default active cluster), keeps the last state per namespace, primes silently on its first evaluation, resets a namespace whose budget was changed or removed, and audits `cost.budget_warning|over|ok`. State is in memory and per replica.

## Kubernetes lifecycle semantics

Axiom does not expose a misleading VM-like "power" abstraction for Kubernetes Pods.

- Workload **Stop** scales Deployments/StatefulSets to zero.
- The previous desired replica count is persisted in `axiom.zyvor.dev/last-replicas` and restored by **Start**.
- **Restart** modifies the Pod template annotation `axiom.zyvor.dev/restarted-at`.
- **Seal / Unseal** apply and remove a deny-all NetworkPolicy for immediate isolation; PacketWolf enriches flow visibility when configured.
- Pod **Evict** uses the policy eviction subresource.
- Node **Drain** cordons the node, skips DaemonSets/mirror Pods/system namespace Pods, then requests evictions.
- KubeVirt VMs get real console *information* (the k8s API subresource path + a copyable `virtctl vnc` command), not a fake embedded VNC client — Axiom has no browser-side VNC/websocket bridge for that subresource.

The default build has no Kubernetes/client-go dependency — it stays runnable in restricted/offline environments. The production provider is selected at compile time.

## HTTP status mapping

`platform.HTTPStatus(err)` decides the status internal/api reports for a provider error, in this order: an explicit `StatusError` (`NewStatusError` / `notFoundf`) wins; then real `*apierrors.StatusError` values (kubernetes build: 404 / 403 / 401 / 409 / 400 / 504 / 429); then a shared message heuristic (`httpStatusFromMessage`, used by **both** builds) that maps hand-written phrasing — "not found" → 404, "already exists" → 409, "is required" / "must be" / "must not" / "unsupported" / "invalid …" / "unknown …" → 400, "cannot …" → 403; anything else is 500. Providers should word validation errors to match, or wrap them with `NewStatusError`, so a bad request never reads as a server outage. Errors that keep their `%w` chain (e.g. per-pod eviction failures joined with `errors.Join`) keep their classification.
